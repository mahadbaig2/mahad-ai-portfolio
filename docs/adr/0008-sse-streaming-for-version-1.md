# ADR-008: Server-Sent Events (SSE) for Assistant Streaming

- **Status**: Partially Superseded by ADR-0010 (Preserved as Historical Record)
- **Date**: 2026-09-04
- **Author**: Antigravity & Mahad
- **Superseded By**: [ADR-0010](0010-elevenlabs-conversational-companion.md) (Voice transport only)

> [!NOTE]
> **Historical Record**: Partially superseded by [ADR-0010](0010-elevenlabs-conversational-companion.md). SSE remains the active transport for full text chat and the compact text chat widget. The strict exclusion of real-time conversational transport has been superseded to permit ElevenLabs-managed real-time transport for conversational voice. Preserved without modification to original engineering reasoning.

## Context
Interactive assistant interactions require real-time streaming of tokens, intermediate pipeline progress events (e.g. `classifying`, `searching`, `grading`, `generating`), and final citation metadata. Protocol choices include bidirectional WebSockets, real-time WebRTC, or HTTP Server-Sent Events (SSE).

## Decision
Use **Server-Sent Events (SSE)** over standard HTTP/2 for all assistant interaction in Version 1:
- Client initiates requests via standard HTTP `POST /api/chat` and receives an SSE event stream (`text/event-stream`).
- Events stream structured JSON payloads for:
  - `progress`: Current LangGraph node execution and inspector timing data.
  - `token`: Incremental response tokens generated by the LLM.
  - `citation`: Final verified source citations and confidence scores.
  - `error`: Structured, user-safe error messages and fallback suggestions.
- WebSockets and WebRTC are intentionally excluded from Version 1 (recorded in `docs/backlog.md`).

## Consequences

### Positive
- Works natively over standard HTTPS without sticky sessions, firewall issues, or complex WebSocket proxying through Cloudflare Pages and Hugging Face Spaces.
- Native browser `EventSource` / standard fetch streaming support with automatic reconnection handling.
- Bounded stateless execution: Each query is an independent request-response stream, avoiding lingering connection leaks or zombie WebSocket states.

### Negative / Trade-offs
- Unidirectional only (server to client). Client messages must be sent as new HTTP requests; this is ideal for turn-based chat, but does not support full-duplex simultaneous voice conversation (which is deferred to post-V1).
